# 高级 RAG 技术

## 查询改写

用户的原始提问可能不适合直接检索:可能太口语化、太模糊,或者一个问题里包含多个子问题。查询改写(Query Rewriting)用大语言模型把原始查询改写成更适合检索的形式。

常见的查询改写技术包括:

查询扩展:把"RAG 效果不好怎么办"扩展为"RAG 检索质量优化方法、召回率提升、重排序"等多个检索友好的表述。

子查询分解:把"对比 RAG 和微调的优缺点"分解为"RAG 的优点和缺点"、"微调的优点和缺点"两个子查询,分别检索后合并结果。

HyDE(Hypothetical Document Embeddings,假设性文档嵌入):让大模型先对问题生成一个假设性的回答,再用这个假设回答的向量去检索。假设回答提供了另一种检索表达。它能否改善检索,需要在具体语料上评估。

## Agentic RAG 与自我纠错

朴素 RAG 是单向流水线:检索一次,不管检索质量如何都直接生成。Agentic RAG 引入了"代理"的决策能力,让系统能对中间结果进行评估并自主决定下一步动作。

CRAG(Corrective RAG,纠错式 RAG)在检索后评估结果:检索完成后,先用一个轻量评估器给每个检索结果打分,分为正确、错误、模糊三档。如果结果正确,直接进入生成;如果结果错误或模糊,则触发纠错动作,比如改写查询重新检索,或者扩大检索范围。

Self-RAG 则更进一步,训练模型在生成过程中输出特殊的反思标记(reflection tokens),自主决定何时需要检索、检索结果是否相关、生成的内容是否有据可依。

检索评估和纠错会增加延迟及 API 调用。本项目只在所有候选块被判为不相关时改写查询,重试一次;重试结果不再评分。

## GraphRAG 与知识图谱

仅检索相似片段可能遗漏跨文档关系,例如"这份年报中各业务线之间的关联是什么"。

GraphRAG 由微软研究院于 2024 年提出:在索引阶段用大模型从文本中抽取实体和关系,构建知识图谱,并对图谱做社区检测,为每个社区生成摘要。查询时,全局性问题走社区摘要路径,局部性问题走实体子图路径。

LightRAG 结合知识图谱和向量检索,采用双层检索机制。本项目没有实现 GraphRAG 或 LightRAG。

## RAG 评估

RAG 评估可分别考察生成内容和检索内容。以下三个维度用于描述不同问题:

忠实度(Faithfulness):回答是否忠于检索到的上下文,有没有编造上下文中不存在的内容。它检查回答与给定上下文的一致性。

答案相关性(Answer Relevancy):回答是否切题,是否真正回应了用户的问题。

上下文相关性(Context Relevancy):检索到的上下文与问题的相关程度,衡量检索模块的质量。

LLM-as-Judge 把问题、上下文和回答交给模型,按预定义标准打分。本项目的评估脚本采用这种方式,评分结果仍需人工抽查。
